# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-user Flask app for entering income/expense records from a phone. Each submission is appended as a row to a Google Sheets spreadsheet ("Доходи" / "Витрати" worksheets) — there is no database. Deployed on Render's free plan via gunicorn.

The UI, comments, commit messages, and docs are in Ukrainian. Match that language when writing user-facing strings, comments, and docstrings.

## Commands

Package/venv management is `uv` (Python 3.13, `uv.lock` is committed).

```powershell
uv sync                              # install deps into .venv
uv run python app.py                 # local dev server on :5000
uv run pytest                        # all tests
uv run pytest -v                     # verbose
uv run pytest tests/test_validation.py::TestValidateAmount::test_accepts_valid_amounts
uv run pytest -k validate_date       # by name
```

Render build/start commands: `pip install uv && uv sync --frozen --no-dev` / `uv run gunicorn app:app`.

## Pre-commit hook

`hooks/pre-commit` runs the full pytest suite and aborts the commit on failure. It is enabled via `git config core.hooksPath hooks` (already set in this clone; re-run after a fresh clone). Tests must pass before any commit — don't bypass with `--no-verify`.

## Architecture

Everything lives in a handful of root-level files:

- `app.py` — the whole application: env loading, Google Sheets client, validation helpers, auth, and all routes (`/login`, `/logout`, `/`, `/submit`, `/delete`, `/edit`, `/stats`, `/currency`, `/currency/rates`, `/reports/send`).
- `config.py` — `CATEGORIES` (expense/income lists with emoji prefixes), `COLUMN_ORDER`, and the two worksheet names. Edit categories here, not in `app.py`.
- `templates/index.html` — the form, the "Останні записи" block, the edit modal, and the "Статистика" modal. All client-side JS (category switching, pre-submit validation, theme toggle, delete confirmation, edit modal, stats fetch/render) is inline in this file, in one `<script>` block per feature. `templates/login.html` is the password gate.
- `static/style.css` — CSS custom properties themed by `data-theme` on `<html>`; theme is chosen by an inline script before paint to avoid a flash, persisted in `localStorage`.
- `main.py` and `test.py` are scratch/leftover files, not part of the app.

Key structural points:

- **Sheets write path**: `append_row(entry_type, row)` maps the row dict through `COLUMN_ORDER` into a positional list, so the sheet's column order must match `COLUMN_ORDER`. The gspread client is lazily created and cached in the module-level `_gs_client`.
- **Categories and subcategories**: the editable category configuration is persisted in `categories.json`. `subcategories` maps each entry type to `{parent_category: [subcategory, ...]}`; a subcategory can belong to only one parent category. The optional `subcategory` field is the final column in both `COLUMN_ORDER` and `DELETED_COLUMN_ORDER`, deliberately appended so old sheet rows remain readable. Validate a non-empty subcategory with `subcategory_is_valid()` on every server write, including split rows.
- **Sheets read path**: `get_recent_entries(ws_name, limit=5)` does a full `get_all_values()` on every `GET /` and delegates to the pure `_rows_to_entries(all_values, limit)`. Failures are caught in `index()` so the form still renders with `recent_error` set — never let a Sheets outage break the page.
- **Sheets delete path**: sheet row numbers shift after every deletion, so a row number alone is not a safe identifier for a page that may have been open for hours. Each rendered entry carries `row_number` plus a fingerprint (`FINGERPRINT_COLUMNS`: date, category, amount, added_at) as hidden form fields; `delete_row` re-reads the row and deletes only if the fingerprint still matches, returning `False` otherwise so the user is told to reload. Preserve that read-then-compare guard when touching this code — dropping it silently deletes the wrong record.
- **Sheets edit path**: uses the same fingerprint guard as delete — `update_row` re-reads the row, compares fingerprint, and only updates if it matches. Editable fields: date, category, amount, note. System fields (submitted_at, added_at, device_info) are never modified by `update_row`. The per-entry "📝" button is rendered directly inside the `recent_item` Jinja macro (`data-edit-*` attributes carry the entry's values and fingerprint) — don't move it to a JS-side DOM-injection pass, that was tried and is fragile (easy to get the dataset-key mapping wrong and silently render no button).
- **Split expenses** (`use_split` checkbox): allow splitting one entry across multiple categories. When submitted, `append_row` creates multiple sheet rows (one per category), all with the same `split_id` (UUID). The grouped display (`_group_split_entries`) merges these back into a virtual single entry for the UI: categories are concatenated with " + ", `split_total_amount` is calculated from all rows, and `split_entries` contains the original rows. When editing a split, the modal switches to a split-editing interface (similar to the submit form): user can add/remove categories, adjust amounts, and the last amount auto-calculates as remainder from the total in the (still visible) amount field. Editable fields: date, note, category/amount breakdown. `update_row(split_id=..., split_breakdown=...)` rewrites the group atomically and **adds/removes sheet rows when the category count changes** — skipping that leaves orphaned rows carrying the old split_id. Deletes remove all rows in the split atomically via `delete_row(split_id=...)`, archiving all to the DELETED sheet.
  - **Split identity is `split_id`, not `row_number`.** For the split paths, `_split_rows()` locates rows by the UUID and `_split_fingerprint_matches()` accepts a match against *any* row of the group; `row_number` is ignored. A UUID can never point at somebody else's record, so the row-shift hazard the fingerprint exists to guard against doesn't apply — whereas re-reading `row_values(row_number)` positionally made every split delete/edit fail with "Запис уже змінився" as soon as anything shifted the numbering (including a manual edit in the sheet). Don't reintroduce a positional re-read here. The single-row paths still use `row_number` + strict fingerprint, and that's correct for them.
  - The edit modal hides the category field for splits. It is `required`, so the JS must also `disabled = true` it — a `required` control that is `display:none` makes the browser refuse to submit *and* fail to show a message, so "Зберегти" silently does nothing. `closeEdit()` has to re-enable it, since `form.reset()` doesn't touch `disabled`.
  - Split entries never carry a foreign currency — see "Currency-denominated entries" below; the currency toggle is hidden/reset for split editing the same way the category field is.
- **Stats path**: `GET /stats` is a JSON endpoint (not a page), fetched lazily from the modal's JS only when it's opened — it's a second full `get_all_values()` per worksheet (via `get_period_stats` → `_all_entries` → `_aggregate_stats`), so it deliberately isn't loaded on every `GET /` the way recent entries are. `_aggregate_stats` fills every date in the range with `0` (via `_date_range`) even where no entries exist, so the daily chart never has gaps. Malformed amounts (manual sheet edits) are skipped via `validate_amount`, same as elsewhere. The range is clamped to `MAX_STATS_RANGE_DAYS` (1825, ~5 years) server-side regardless of what the client requests; if clamped, a `warning` field is included in the JSON response. The modal has separate views: **daily** retains its rolling 7/30/90-day presets, current/previous calendar-month presets, and custom range; **monthly** has independent six-month, one-year, and custom-range filters. The monthly comparison is calculated client-side from returned daily data, so it adds no API calls: it renders income, expense, net result, and net-result percentage of income in a table and grouped bar chart. Keep the views' ranges independent when editing this UI. Accepts optional `currency` parameter (`UAH`, `USD`, or `EUR`); for a foreign currency, converts via `_aggregate_stats_foreign()`, which calls `get_exchange_rate(date, currency)` for NBU rates per transaction date. Rates are cached in `_exchange_rates_cache` keyed by `(currency, date)` for the session. Before the per-entry loop runs, `_prefetch_exchange_rates()` fetches every date missing from the cache concurrently (`ThreadPoolExecutor`, capped by `EXCHANGE_RATE_MAX_WORKERS`) — fetching a year of rates one at a time made that view take minutes. Note this `currency` parameter (the display currency for the stats view) is unrelated to the per-entry `currency` field described below: stats always sums the `amount` (UAH) column and optionally converts the *totals* for display, so a currency-denominated entry is already counted in UAH there — nothing in `/stats` needed to change.
- **Currency-rate analytics page**: `templates/currency.html` (`GET /currency`) is a standalone page — not a modal, and not scoped to the user's income/expense data — reachable via the 💱 button in the "Статистика" modal header. Its data comes from `GET /currency/rates`, a JSON endpoint mirroring `/stats`'s period/clamp/warning conventions (`validate_date`, `MAX_STATS_RANGE_DAYS`, swapping a reversed range) but only accepts `currency=USD|EUR` (defaults to USD; anything else, including `UAH`, falls back to USD — there's no "no conversion" option here since the whole page is about a foreign currency's rate). `get_currency_period_analysis()` returns a daily `series` plus `start_rate`/`end_rate`/`change_percent`/`direction` (`"devaluation"` when the rate rose — UAH buys less — `"revaluation"` when it fell, `"stable"` at 0%, or all `None` when NBU returned nothing for the period). The page shows one currency's line chart at a time by design (a toggle, not simultaneous USD+EUR) since overlaying two different rates on one axis is misleading.
  - **Period fetch, not per-date fetch**: unlike `get_exchange_rate()` (one NBU request per date, used by `/stats`'s foreign-currency conversion), `get_exchange_rate_range(start, end, currency)` requests the whole span in a single NBU call (`start`/`end` query params on the same `exchange` endpoint) — this page would otherwise cost up to `MAX_STATS_RANGE_DAYS` sequential requests just to draw one chart. Don't change this back to a per-date loop.
  - NBU doesn't publish a rate for every calendar day (e.g. some weekends). `_fill_rate_gaps()` forward-fills missing days from the last known rate, and back-fills a leading gap from the first known rate, so the chart and the start/end comparison never operate on `None` in the middle of the series.
- **Currency-denominated entries** (currency toggle — ₴/UAH, $/USD, €/EUR — next to the amount field, on both the submit form and the edit modal, for income and expense alike): lets the person type an amount directly in USD or EUR instead of UAH. `amount` (the pre-existing column) is unchanged in meaning — it always holds the UAH equivalent, so every existing consumer (`/stats`, email reports, the delete/edit fingerprint, category totals) keeps summing/reading it exactly as before; nothing downstream needed to change. Three columns are appended at the end of `COLUMN_ORDER`/`DELETED_COLUMN_ORDER` (after `subcategory`, same backward-compatible append pattern) for this: `curr_amount` (the amount as typed, in `currency`), `exchange_rate` (UAH per unit of `currency` used for the conversion), and `currency` (`UAH`/`USD`/`EUR`). `currency` is always populated (`"UAH"` for a plain-UAH entry, including every historical row — read back as `""` by `_row_to_entry`'s zero-padding, which the templates treat the same as `"UAH"`); `curr_amount`/`exchange_rate` are populated only when `currency` is `USD` or `EUR` — for a UAH entry they're written empty. `_ensure_new_column_headers()` (renamed from the old `_ensure_subcategory_header`, which only ever backfilled one hardcoded header) now backfills however many trailing headers a given sheet is still missing, since a sheet could be missing just `subcategory`, or all four new columns, depending on when it was created.
  - **Rate resolution**: `get_latest_exchange_rate(currency)` — distinct from the period-oriented `get_exchange_rate_range()` above — tries today's NBU rate (Kyiv date), then falls back to yesterday's if NBU hasn't published today's yet. This is independent of the entry's own `date` field: the person is entering the transaction *now*, at *today's* going rate, not backdating a historical conversion. `resolve_currency_amount(currency, curr_amount)` wraps that: on success, `amount = round(curr_amount * rate, 2)`. If NBU is unreachable for both days, it falls back to `rate = 1` and `amount = curr_amount` (identical numeric value in both columns, per product decision — a placeholder rather than a failed submission) and returns a warning string that `submit()`/`edit()` append to the success flash message, e.g. "Запис додано. Курс НБУ недоступний — суму збережено без конвертації в гривні (курс 1)." This mirrors the existing "always succeed, warn instead of block" pattern (`add_emoji_if_missing`, `get_recent_entries`).
  - **Not supported for split expenses.** Splits (`use_split`) stay UAH-only, per product decision — `append_row`'s split branch always writes `currency = "UAH"` and leaves `curr_amount`/`exchange_rate` empty, regardless of whatever the (hidden, in that flow) currency selector holds, and `submit()`'s split branch always uses the raw entered amount (never a currency-converted one). `index.html`'s JS hides and resets the currency toggle to UAH whenever the split checkbox is checked, and disables its buttons.
  - **Formatting**: `curr_amount` and `exchange_rate` go through the same `_amount_for_sheet()` comma-decimal formatting as `amount`, for the same reason — a freshly-submitted row and a freshly-edited row must use the same on-sheet representation, or a fingerprint taken from one wouldn't match a re-read of the other.
  - **Editing**: the edit modal's currency toggle defaults to the entry's stored `currency` (`entry.currency`/`entry.curr_amount` are read like any other column — no special-casing needed in `_row_to_entry`; `recent_item`'s `data-edit-amount` supplies `curr_amount` instead of `amount` when the entry is foreign-currency, so the modal opens with the originally-typed value, not the UAH equivalent). Changing currency during edit re-resolves the rate via `resolve_currency_amount()` at save time — the *current* latest rate, not whatever rate the entry originally used, same reasoning as new entries: the person is re-affirming this value now. Switching back to UAH during edit clears `curr_amount`/`exchange_rate` to `""` server-side. The fingerprint (`FINGERPRINT_COLUMNS`) is untouched by any of this — it still keys off `amount` (UAH), which continues to mean the same thing it always did.
- **Last-update timestamp**: `get_last_update_time()` shells out to `git log -1 --format=%cI` in the repo containing `app.py` to find the latest commit (in practice, the latest merged PR) and converts it to Kyiv time via the same `_format_commit_time()` → `KYIV_TZ` path as everything else date-related. It's injected into every template as `last_update` via `@app.context_processor` (`inject_last_update()`), so no route needs to pass it explicitly — `templates/index.html` and `templates/currency.html` render it in the footer, guarded by `{% if last_update %}`. Result is cached in the module-level `_last_update_cache` for the process lifetime (a new deploy is a new process, so the commit can't change underneath a running instance) and never raises — if `git` isn't available in the deploy environment (e.g. a source-only artifact without `.git`), it silently returns `None` and the footer line just doesn't render, the same "don't let this break the page" pattern as `get_recent_entries()`.
- **Emoji suggestion for new categories**: `add_emoji_if_missing(name)` is called from `add_category`, `rename_category`, `add_subcategory`, and `rename_subcategory` before the name is stored. If `has_emoji(name)` is already true, it's a no-op (no LLM call). Otherwise it calls `suggest_emoji(name)`, which asks OpenAI (`OPENAI_MODEL`, default `gpt-4o-mini`) for a single emoji and prefixes it. `get_openai_client()` mirrors `get_client()`'s laziness for Google Sheets — it returns `None` (not an exception) if `OPENAI_API_KEY` isn't set or the `openai` package can't be imported (`_import_openai_client_class()` is split out specifically so tests can force that branch without uninstalling the package). Any failure anywhere in that chain (no client, network, timeout, a response with no emoji in it) is caught by `add_emoji_if_missing`, which **always** returns a name to save — on failure that's just the original, unprefixed name, plus a `warning` string. Routes fold that into the JSON response as `"warning": "..."` alongside `"success": true`; the category/subcategory is never rejected because the LLM failed. The category-add/rename JS in `index.html` shows that warning via the existing `showError()` box after a successful save (reused for warnings too, not just errors). Because emoji-prefixing can fail, duplicate checks in all four routes compare `_category_core_text()` (emoji stripped, casefolded) instead of exact strings — otherwise a manually-typed "Кіно" and a later successful "🎬 Кіно" would coexist as separate categories.
- **Validation is deliberately Flask-free**: `validate_amount` and `validate_date` are plain functions taking raw strings, so `tests/test_validation.py` can test them without app context or network. Keep new validation logic in the same shape. Client-side validation in `index.html` mirrors these rules but is not a substitute for them.
  - **Amount validation** strips all whitespace (including non-breaking spaces U+00A0 from Google Sheets thousands separators) before parsing, then validates as `^\d+(\.\d+)?$`.
  - **Date validation** accepts both ISO format (`YYYY-MM-DD`) and Excel serial numbers (floats 0–60000, covers 1900–2063); the Excel serial is converted via epoch offset to enable importing historical data from Excel files.
- **Auth** is a single shared password (`APP_PASSWORD`) checked against `session["authed"]` by the `@login_required` decorator. No user accounts.
- **Kyiv time, not server time**: Render runs in UTC, but this is a single-user, Kyiv-based app, so anywhere "today" is user-facing — the date field's default/max, `validate_date`'s default upper bound, `/stats`'s default range, and `get_latest_exchange_rate`'s "today"/"yesterday" lookup for currency-denominated entries — goes through `today_kyiv()`, never `date.today()`. `date.today()` reads the server's clock; Kyiv runs 2-3 hours ahead (DST-dependent), so using it directly meant the date field defaulted to yesterday, and even rejected today's actual date as "in the future," for a few hours every night. `today_kyiv()` needs the IANA tz database via `zoneinfo`; Linux (Render) has it built in, Windows doesn't, so local dev needs `tzdata` as an explicit dependency (`uv add tzdata`).
- **Rate limiting**: `flask-limiter` caps `POST /login` at 5/min; `ProxyFix(x_for=1)` is required for the limiter to see real client IPs behind Render's proxy. The 429 handler re-renders the login page with a flash. Storage is in-memory (known limitation, see ROADMAP).
- **Email report (Resend)**: `get_period_summary(start, end)` reads both worksheets and reduces them to `{count, income, expense, net}` (row-level, so a split expense counts as N transactions — same granularity as `_aggregate_stats`). `render_report_text`/`render_report_html` format that into a command-line-styled message (`$ budget --report --period ...`, monospace `JetBrains Mono`, dark `#0d1117` background for the HTML version) with no shared code with the `/stats` charts — this is a separate, much simpler rendering path. `send_report_email(start, end)` posts to the Resend HTTP API (`https://api.resend.com/emails`) rather than SMTP; the API key is inherently send-only (unlike a Gmail App Password, which also grants IMAP/inbox read), so there's nothing to expose if it leaks beyond the sending quota. It's a no-op returning `False` when `RESEND_API_KEY` or `DAILY_REPORT_EMAIL` is unset — the same "silently disabled without a key" shape as the OpenAI emoji feature — and raises (via `response.raise_for_status()`) on a non-2xx Resend response, which callers catch and flash to the user.
  - **Yesterday's report is sent by catch-up, not by a clock-based scheduler.** Render's free tier sleeps idle web services, so a `time.sleep()`-based "wait until 22:00" loop would frequently never fire. Instead, `@app.before_request` calls `maybe_send_yesterday_report()` on every request; it checks `daily_report_state.json` (`{"last_sent_date": "YYYY-MM-DD"}`) and sends only if yesterday (Kyiv) isn't recorded yet. A successful send persists the date; a failure persists nothing, so the very next request (e.g. the next time the sleeping dyno wakes up) retries automatically. `_daily_report_confirmed_date` is an in-process cache of the last confirmed date so most requests skip the file read entirely; `_daily_report_lock` guards the read-check-send-write sequence against concurrent requests racing right after a cold start. This file is gitignored and not treated as a source of truth — it can be absent or stale after a redeploy (Render's filesystem isn't persistent across deploys), and the worst case is one duplicate or one skipped catch-up email, not a broken app.
  - **On-demand path is separate and stateless**: `POST /reports/send` (button "📧" in the header, modal with `start`/`end` date inputs) calls the same `send_report_email()` directly for whatever period the user picks — no state, no catch-up logic, always attempts to send. `start_date == end_date` is valid (a single day) since `_report_period_label()` collapses it to one date instead of a range. The modal has its own preset buttons (`#report-presets`: last 7 days, current calendar month, previous calendar month) that only fill the `start`/`end` date inputs client-side — mirrors the date math already used by `/stats`'s calendar-month presets in the same file, but is a separate, independent block (`#report-presets .stats-preset`, not `.stats-preset[data-days]`/`[data-period]`) so it doesn't interact with the stats modal's own preset state. Sending is still a separate click ("Надіслати"); presets never submit the form themselves.

## Environment

Required env vars (see `.env.example`), read at import time — `app.py` raises `KeyError` without them: `FLASK_SECRET_KEY`, `APP_PASSWORD`, `GOOGLE_SHEET_ID`, `GOOGLE_CREDENTIALS_JSON` (the service-account JSON key, on one line).

Optional: `OPENAI_API_KEY` (read via `os.environ.get`, so its absence never raises — no `conftest.py` entry needed for it, unlike the required four above) enables the emoji-suggestion feature; `OPENAI_MODEL` overrides the model (default `gpt-4o-mini`). `RESEND_API_KEY` and `DAILY_REPORT_EMAIL` (also `os.environ.get`, same "absence never raises" shape) enable the email report feature; `RESEND_FROM_EMAIL` overrides the sender (default `onboarding@resend.dev`, which only delivers to the address registered on the Resend account — fine for this single-user app, but a verified custom domain is needed for any other recipient).

`tests/conftest.py` stubs out `dotenv.load_dotenv` and sets fake values for all four *before* importing `app`. Any new module-level env read in `app.py` must be added there too or the whole suite fails to collect.

Two test-harness details worth knowing:

- The rate limiter is disabled via `limiter.enabled = False`, **not** `config["RATELIMIT_ENABLED"]` — flask-limiter reads that config key once during `init_app()`, which happens at `app.py` import time, so setting it from a fixture is too late. Getting this wrong is quiet: the suite passes until it accumulates more than 5 `POST /login` calls per minute, then unrelated tests start failing with 429.
- `logged_in_client` sets `session["authed"]` directly through `session_transaction()` rather than posting the login form, so tests neither depend on the login flow nor consume the login rate limit.
- Tests that need Sheets monkeypatch `app.get_client` with a fake client (see `tests/test_delete.py`, `tests/test_edit.py`, `tests/test_stats.py`) or replace `app.get_recent_entries`/`app.delete_row`/`app.update_row`/`app.get_period_stats` outright. Nothing in the suite touches the network — never start the real dev server or hit the live Google Sheet to verify a change; the fake-client pattern is the verification path, and it also avoids ever needing the real `.env` secrets outside of actual local/Render runs.
